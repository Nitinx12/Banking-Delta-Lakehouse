    Reporting: Banking Delta Lakehouse

    Dynamic PDF reporting for the pipeline. When a run finishes, an alert fires or a digest is due, a Python builder reads the audit schema, scores what happened, renders LaTeX from Jinja templates, compiles reports/main.tex with pdfLaTeX and produces report.pdf. Airflow attaches the PDF to the summary mail. The report adapts to the news: a healthy night is a short verdict with a few charts, a bad night adds incident chapters, evidence and runbook pointers, and a serious one also produces a separate incident PDF.

    Colour legend: docs/PIPELINE.md. Rules for agents in AGENTS.md always win on conflict; this page adds the reporting specific ones. Related: docs/AUDIT.md (data source), docs/AIRFLOW.md (DAG and mail), docs/RUNBOOK.md (actions linked from incidents), docs/TESTING.md (test tiers).

    1. Goals and non goals

    Goals:

    • Page one answers in ten seconds: is the pipeline healthy, what broke, what do I do next.
    • Fully dynamic: chapters, charts, flow colours and wording come from data, never from hand edited text. Any minor or major event changes the report.
    • One design system: Jinja for structure, LaTeX for typography, matplotlib for charts, TikZ for the pipeline flow.
    • Delivered by the existing Airflow summary mail as an attachment, with no new mail stack.
    • Reproducible: the same context.json always produces the same PDF.

    Non goals:

    • It does not replace the DQ gates, the watchdog or the Streamlit dashboard.
    • It never changes pipeline state. It is a read only consumer of audit.* and the warehouse metadata.
    • It never shows row values, PII or credentials. Counts, names and statuses only, the same contract as audit_reader.py.
    • A failed report never turns a green pipeline run red.

    "Event driven" here means severity is evaluated at defined trigger points, not that a file watcher runs LaTeX. The trigger points are: the end of every daily run (all_done, so failed runs are reported too), watchdog alerts for runs that never reach their end ([MISSED], [STUCK]), the weekly digest schedule, and a human running make report.

    3. Rules for agents

    1. Read AGENTS.md, docs/AUDIT.md and sql/scripts/02_audit_tables.sql before writing a query. Use column names from the DDL, never from this page.
    2. Read only. The collector may SELECT from audit.*, the registry and MAX(_loaded_at) style freshness probes. No INSERT, UPDATE, CALL or DDL. Open the connection with default_transaction_read_only = on.
    3. No row values, PII, secrets or connection strings in context.json, charts, LaTeX or mail. Every free text field (error messages, violation messages) goes through the existing redaction (redact.py and src.utils.audit._redact) and is cut to 300 characters. Do not copy the regexes. If importing across packages is awkward, ask before promoting the helper to src/utils/redact.py.
    4. Every value that reaches LaTeX is escaped by the Jinja finalize hook (section 8). Raw LaTeX is allowed only through the explicit raw filter on values built by Python code, never on data from the warehouse.
    5. Compile with -no-shell-escape -halt-on-error. Never enable \write18 or --shell-escape, and never \input a path built from data.
    6. A missing or unknown state is never rendered as success. Same principle as summary.decide_status. Use UNKNOWN (grey) when a step has no audit evidence.
    7. The report derives status from audit.pipeline_runs, audit.table_runs, audit.dq_run and audit.pipeline_errors, never from Airflow task instances. The summary mail layers live Airflow states on top of the same audit rows (summary.collect_task_states, docs/AIRFLOW.md); the report stays audit only so both sides agree on pipeline facts.
    8. Do not "correct" timestamps. Times are shown as stored with their zone label, and the appendix links the open timezone offset issue (docs/TROUBLESHOOTING.md, open issue 3).
    9. Thresholds and severity mappings live in reports/config/report.yaml. Lowering a severity or loosening a threshold needs a human decision, the same way DQ thresholds do.
    10. A report failure degrades, it does not block. Section failures render a visible "section unavailable" box, a compile failure retries in safe mode (section 10), and the Airflow task never sits in the failure gate.
    11. Output is deterministic. Sort every list, fix the random seed, set SOURCE_DATE_EPOCH from the run end time, never print now() inside the document body.
    12. Dependencies are added with uv only (uv add --group reports ...). No pip, no conda, no hand edited lock file.
    13. Style: one short header comment at the top of each file, no paragraph comments and no comments between code lines. SQL is uppercase keywords, one column per line, four space indent. Python passes ruff. Documentation prose uses no hyphens.
    14. Windows safe: pathlib, sys.executable, encoding="utf-8" on every open and read_text, no POSIX only calls, forward slashes inside LaTeX paths.
    15. Do not edit or import anything under reports/legacy/. It is reference material only.

    5. Report kinds and chapters

    Kind File Produced when Audience question
    daily report.pdf every banking_delta_daily run, always what happened last night
    incident incident.pdf any event with severity MAJOR or CRITICAL, plus watchdog alerts what broke, why, what now
    weekly weekly.pdf banking_report_weekly, Monday 08:00 Asia/Kolkata is the platform trending well

    The incident PDF is produced in addition to report.pdf, so the daily report stays consistent every day. Both are attached to the same mail.

    Chapter template Content Charts and visuals Included in
    01_summary verdict banner, KPI cards, top events, next actions none, cards only all kinds
    02_flow the 9 gated steps and 3 extracts as a coloured flow TikZ flow daily, incident
    03_timeline task durations, retries, critical path task timeline daily, incident
    04_volumes rows extracted and landed per table, deviation from trailing median volumes dumbbell, layer bars daily, weekly
    05_dq DQ gate results per layer and check, violation counts DQ heatmap daily when any DQ row exists, incident, weekly

    Page budget: daily 4 to 8 pages, incident 2 to 5, weekly 4 to 6. A healthy daily report must fit page one plus the appendix.

    6. Events and severity

    Every report starts from a list of events. An event is one fact about the run with a severity, a place and an impact.

    Severity Meaning Verdict label Banner colour
    INFO normal, worth a line (for example a table skipped, no new data) HEALTHY green
    MINOR self healed or low impact (retry used, small deviation) ATTENTION amber
    MAJOR a gate or step failed, data late or partial ACTION REQUIRED red
    CRITICAL run failed, nothing published, or status unknown INCIDENT dark red

    The run verdict is the maximum event severity, and its one-line headline and consequence come from wording: in report.yaml, one entry per severity. Mail subjects keep the existing [SUCCESS|WARNING|FAILED] marker from summary.py; the report verdict appears in the body and in the attachment file name, for example Banking-Delta_daily_20261021_ATTENTION.pdf.

    Rule catalogue

    Rules live in reports/scripts/severity.py, one function per rule, each with a test.

    Rule Signal (source) Condition Severity
    R001 audit.pipeline_runs.status FAILED CRITICAL
    R002 audit.pipeline_runs.status PARTIAL MAJOR
    R003 audit.dq_run a layer suite has status FAIL MAJOR
    R004 publish table_runs or DQ row_count_source_vs_published publish not SUCCESS, or published rows differ from source MAJOR
    R005 audit.pipeline_errors.error_category CONNECTION or SPARK on the final attempt MAJOR
    R006 audit.pipeline_errors.error_category CONCURRENCY that a retry resolved MINOR
    R007 audit.table_runs.attempt_number greater than 1 for any table MINOR
    R008 audit.data_quality_results WARNING severity check not passing MINOR
    R009 table_runs.rows_landed vs trailing median deviation above volume_deviation_ratio MINOR
    R010 full load table with zero rows landed always MAJOR
    R011 run duration vs trailing median above duration_regression_ratio MINOR
    R012 freshness from MAX(_loaded_at) and the contract window window exceeded contract severity (WARNING maps to MINOR, ERROR to MAJOR)
    R013 DQ schema_contract or contracts/ drift any violation MAJOR
    R014 watchdog [MISSED] or [STUCK] alert raised MAJOR
    R015 watchdog [WATCHDOG-ERROR] or a step with no audit evidence status unknown CRITICAL
    R016 collector section raised an error the section degraded MINOR
    R017 table_runs.status SKIPPED because no new data INFO
    R018 pipeline_runs counts vs the collected table_runs list any count disagrees with the tables MINOR

    7. Data collection

    reports/scripts/collect.py builds one dictionary and writes data/context.json. Each section is collected in its own try block so one failure degrades only that section and is recorded in sections_failed (rule R016).

    Section Source Content
    meta arguments, src/utils/config.py, git kind, ids, env, git sha, versions
    run audit.pipeline_runs status, counts, start, end, duration
    steps audit.table_runs, audit.dq_run the 9 gated steps and 3 extracts with state and duration
    tables latest attempt per table in audit.table_runs status, rows extracted, rows landed, watermark start and end, attempts
    dq audit.v_dq_latest, audit.dq_run, audit.data_quality_results per layer, per check status and violation count
    errors audit.pipeline_errors category, severity, redacted message
    freshness registry plus MAX(_loaded_at) per landing table age in seconds, window, breach flag
    trends last trend_runs rows of audit.pipeline_runs duration, status, rows, failures per run
    events output of severity.py the event list and the verdict

    Fixtures

    data/fixtures/ holds synthetic contexts only, with invented table counts and no real values: healthy, minor_retry, major_dq_fail, critical_failed_run, weekly. They drive tests, the CI render check, template development and design reviews, so the whole report can be built with no database.

    8. Rendering with Jinja and LaTeX

    LaTeX uses braces and percent signs everywhere, so the Jinja environment uses custom delimiters.

    Purpose Delimiter Example
    Statement \BLOCK{ ... } \BLOCK{for e in events}
    Output \VAR{ ... } \VAR{run.status}
    Comment \#{ ... } removed from output
    Line statement %% %% if events
    Line comment %# removed from output

    Limits that follow from this: no dict or set literals with braces inside \VAR{} or \BLOCK{}, because the first } closes the tag. Compute such values in Python. StrictUndefined is on, so a typo in a template fails the build loudly in tests rather than printing a blank in a bank report.

    reports/scripts/render.py:

    # LaTeX safe Jinja environment for the report templates.
from pathlib import Path

import jinja2

_TEX_MAP = {
    "\\": r"\textbackslash{}",
    "&": r"\&",
    "%": r"\%",
    "$": r"\$",
    "#": r"\#",
    "_": r"\_",
    "{": r"\{",
    "}": r"\}",
    "~": r"\textasciitilde{}",
    "^": r"\textasciicircum{}",
}


class RawTeX(str):
    pass


def tex_escape(value: object) -> str:
    if isinstance(value, RawTeX):
        return str(value)
    text = "" if value is None else str(value)
    return "".join(_TEX_MAP.get(ch, ch) for ch in text)


def ident(value: object) -> RawTeX:
    text = tex_escape(value)
    return RawTeX(
        text.replace(r"\_", r"\_\allowbreak{}").replace(".", r".\allowbreak{}")
    )


def breakable(value: object) -> RawTeX:
    parts = []
    for part in re.split(r"([^A-Za-z0-9\s])", "" if value is None else str(value)):
        if not part:
            continue
        parts.append(
            tex_escape(part)
            if part.isalnum() or part.isspace()
            else r"\allowbreak{}" + tex_escape(part)
        )
    return RawTeX("".join(parts))


def make_env(*template_dirs: Path) -> jinja2.Environment:
    env = jinja2.Environment(
        loader=jinja2.FileSystemLoader([str(p) for p in template_dirs]),
        block_start_string=r"\BLOCK{",
        block_end_string="}",
        variable_start_string=r"\VAR{",
        variable_end_string="}",
        comment_start_string=r"\#{",
        comment_end_string="}",
        line_statement_prefix="%%",
        line_comment_prefix="%#",
        trim_blocks=True,
        lstrip_blocks=True,
        autoescape=False,
        undefined=jinja2.StrictUndefined,
    )
    env.finalize = tex_escape
    env.filters.update({"raw": RawTeX, "ident": ident, "breakable": breakable})
    return env

    finalize escapes every \VAR{} output automatically, so escaping is the default and opting out is explicit. Additional filters to implement and test: fmt_int (thin space thousands), fmt_pct, fmt_dur (1h 05m), fmt_ts (with zone label), state_colour, severity_colour, plural.

    Template conventions:

    • One chapter per file, each starting with \section{...} and ending with a blank line.
    • Use partials for anything repeated twice: KPI card, event row, status pill, the "section unavailable" box.
    • Identifiers in tables use \texttt{\VAR{x | ident}} so long names such as raw.card_transactions break cleanly.
    • Free text in a table cell uses \VAR{x | breakable}, which allows a break at every punctuation mark. Without it a long message such as rows_landed=22500, cannot wrap and pushes the cell past the margin.
    • No logic that belongs in Python. Templates loop, branch on presence and format. Sorting, thresholds, joins and colour decisions are computed before rendering.
    • Free text from the warehouse is always plain \VAR{}. Only Python built values use raw.

    Chapter excerpt (chapters/partials/event_table.tex.j2):

    \BLOCK{if events}
\begin{longtable}{@{}p{2.4cm}p{3.6cm}p{9.6cm}@{}}
\toprule
\textbf{Severity} & \textbf{Where} & \textbf{What happened} \\
\midrule
\BLOCK{for e in events}
\severitytag{\VAR{e.severity | lower}} & \texttt{\VAR{e.subject | ident}} & \VAR{e.message} \\
\BLOCK{endfor}

\end{longtable}
\BLOCK{else}

\BLOCK{endif}

    Typography

    Use Font Notes
    Body, tables, headings Inter (Regular, Italic, SemiBold, SemiBold Italic) tabular numerals on, so digit columns align

    Both families are open licence. The .ttf files and their licence texts are in reports/fonts/ and committed, because CI and the Airflow image have no network to fetch fonts. If a file is missing the build must still succeed:

    % Font setup with a fallback so a missing file never breaks the build.
\usepackage{fontspec}
\IfFileExists{fonts/Inter-Regular.ttf}{
  \setmainfont{Inter-Regular.ttf}[Path=fonts/, BoldFont=Inter-SemiBold.ttf,
    ItalicFont=Inter-Italic.ttf, BoldItalicFont=Inter-SemiBoldItalic.ttf,
    Numbers=Monospaced]
}{
  \setmainfont{TeX Gyre Heros}
}

    Do the same for the mono font with TeX Gyre Cursor as the fallback. Never ship a font without its licence. If the font files are absent, ask a human to add them; do not invent or download them from an unknown source.

    Current state. The font files are in the repository: Inter 4.1 and JetBrains Mono 2.304 (SIL OFL 1.1), each next to its licence text in reports/fonts/. The style file loads them with fontspec and reports/latexmkrc sets $pdf_mode = 5 (XeLaTeX) for that. A pdfLaTeX build (an old checkout, or a manual pdflatex main.tex) keeps the scalable Latin Modern family (\usepackage{lmodern}), which microtype needs to expand. Latin Modern is metric compatible with the layout, so the fallback changes the glyphs, not the page structure. The charts register the same files with matplotlib, so the document and the figures share one typeface. Provenance and the update procedure: reports/fonts/README.md.

    Scale: base 10.5 pt, line spacing 1.2, section titles 16 pt, subsection 12 pt, table text 9 pt, captions 8.5 pt. A4, margins 20 mm left and right, 22 mm top and bottom, text width about 170 mm.

    Pipeline flow diagram

    The flow is a TikZ picture generated from the steps list, so node colours and badges follow the run. Node fill is the layer colour, node border and badge are the status colour, the label carries the step name and duration. Node ids are slugs made by flow.py (n01, n02, and so on) so they never need escaping. Coordinates come from a fixed grid in flow.py: three extract nodes stacked on the left, then the gated chain, then publish and finalize.

    \begin{tikzpicture}[every node/.style={font=\footnotesize}]
\BLOCK{for node in flow.nodes}
\node[flowstep, \VAR{node.layer | raw}, \VAR{node.state | raw}] (\VAR{node.id | raw}) at (\VAR{node.x | raw}, \VAR{node.y | raw}) {\VAR{node.label}\\{\scriptsize\VAR{node.duration}}};
\BLOCK{endfor}
\BLOCK{for edge in flow.edges}
\draw[flowarrow] (\VAR{edge.src | raw}) -- (\VAR{edge.dst | raw});
\BLOCK{endfor}
\end{tikzpicture}

    flowstep, the layer names (raw, staging, analytics, marts, publish, audit) and the state names (ok, warn, bad, idle) are TikZ styles defined in the style file. The node style is called flowstep and not step, because step is a PGF key that already means something else. Values passed with raw are validated by Python against an allow list before rendering.

    10. The builder

    uv run python -m reports.scripts.build --kind daily --dag-id banking_delta_daily --dag-run-id "<id>"
uv run python -m reports.scripts.build --kind incident --dag-run-id "<id>"
uv run python -m reports.scripts.build --kind weekly
uv run python -m reports.scripts.build --fixture reports/data/fixtures/major_dq_fail.json
    Flag Meaning
    --kind daily\|incident\|weekly which chapter set to build
    --dag-id, --dag-run-id which run to report, defaults to the latest
    --fixture PATH skip the database and use a context file
    --all-fixtures build every tracked fixture, one report each
    --no-pdf stop after rendering .tex (hermetic, no TeX needed)
    --no-charts safe mode, no figures and no TikZ flow
    --out DIR output root, wins over REPORT_OUTPUT_DIR
    --strict treat any degraded section as an error, for tests

    Steps, in order, with a total budget under 60 seconds in CI and under 2 minutes in Airflow:

    1. Collect and write data/context.json, validate against the schema. The same document is copied next to the PDF as runs/RUN_KEY/context.json.
    2. Evaluate rules, attach events and verdict, decide which kinds to build.
    3. Draw charts into figures/, skipping any that fail.
    4. Render build/meta.tex, build/manifest.tex and the chapters. A chapter that still holds a \VAR{ or \BLOCK{ tag fails the build with exit code 2.
    5. Compile with latexmk -jobname=report main.tex. The LaTeX state of the job is deleted first, so a broken .aux from an earlier run cannot break this one. On failure retry once with --no-charts (safe mode) and mark the report "degraded" on page one.
    6. Copy to output/runs/RUN_KEY/<pdf name> and output/<pdf name> (latest): report.pdf for the daily, incident.pdf, weekly.pdf. Write the redacted compile log to build/<jobname>.log (report.log, incident.log, weekly.log). Prune runs older than REPORT_RETENTION_DAYS.
    7. Print a one line JSON result (kind, verdict, pages, path, degraded).

    Exit codes: 0 built, 2 render or schema error, 3 compile failed even in safe mode, 1 usage error. RUN_KEY is the run id reduced to [A-Za-z0-9_] by paths.py.

    • Update airflow/tests/test_dag_integrity.py: the task exists, trigger_rule is all_done, it sits after finalize_audit and before send_pipeline_summary, it is not linked to the failure gate, and the retries and timeout match.

    Image and compose

    TeX Live is large (roughly 500 to 800 MB). Recommended option: install it in the Airflow worker image, so the task runs exactly what python main.py and make report run, with no Docker socket mounted into Airflow. Both Dockerfiles read the same package list.

COPY reports/apt-packages.txt /tmp/apt-packages.txt

    && xargs -a /tmp/apt-packages.txt apt-get install -y --no-install-recommends \
    && rm -rf /var/lib/apt/lists/* /tmp/apt-packages.txt

    Also copy reports/ into the image and run uv sync --frozen --group reports. Never mount /var/run/docker.sock into an Airflow container for this feature. reports/apt-packages.txt starts with latexmk, texlive-xetex, texlive-latex-recommended, texlive-latex-extra, texlive-pictures, texlive-fonts-recommended and fontconfig; trim or extend it after the first clean compile. texlive-fonts-recommended provides Latin Modern, which the pdfLaTeX fallback needs for microtype; fonts-inter is the system copy of Inter for the XeLaTeX build, next to the bundled files in reports/fonts/.

    reports/Dockerfile is the standalone builder: it installs the same package list, adds the report runtime (jinja2, jsonschema, pyyaml, matplotlib, psycopg2-binary, python-dotenv) and copies src/ and reports/ into /work. The entry point compiles every fixture, so docker run needs no arguments.

    Rules that must not break

    • The report only reads. It never writes to the warehouse, Databricks or audit.*.
    • No row values, PII, secrets or credentials in context, figures, LaTeX, logs or mail.
    • Every value is escaped by default; shell escape stays off.
    • Unknown is never shown as success; a failed report never fails the pipeline.
    • Same context in, same PDF out.
    • Thresholds and severities change only with human approval.
    • The mail path is the existing one; attachments extend it, they do not replace it.
