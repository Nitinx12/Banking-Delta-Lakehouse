    Architecture — Banking-Delta-Lakehouse

    The blueprint of the project. Read this first; AGENTS.md holds the rules for working in the repo, and docs/*.md drill into each subsystem. If this file and the code disagree, the code wins — then fix this file.

    Banking-Delta-Lakehouse is a daily lakehouse pipeline: three source systems are landed into PostgreSQL with PySpark, transformed by SQL stored procedures through four layers (raw → staging → analytics → marts), gated by data-quality suites at every step, and finally published to Databricks Delta where a read-only dashboard serves them. Airflow schedules it; main.py runs the identical steps by hand.

    2. Design principles

    1. One way to run the pipeline. main.py and the Airflow DAG call the same scripts and the same SQL. Airflow adds scheduling, retries, pools and alerting — it contains no pipeline logic of its own (airflow/dags/banking_delta_daily.py).
    2. Gate before the next layer. A failing step stops the run; a critical data-quality failure blocks publish. Nothing downstream ever reads a half-loaded layer.
    3. Idempotent by construction. Every load is safe to run twice with the same input.
    4. Watermarks move only with the data. A watermark advances inside the same transaction as the write, so a crash never loses or double-counts rows.
    5. Audit survives failure. Audit rows are written in their own short transactions; the DQ gate COMMITs its verdict before it RAISEs.
    6. Correct types. Money is NUMERIC(18,2) / Decimal, never float. All instants are timezone-aware UTC; Spark JVM + SQL session run in UTC.
    7. Layer ownership is strict. Each schema is written by exactly one owner (see §5).
    8. Hermetic by default. CI and the local gate need nothing external; anything that touches real data or credentials is scheduled, gated and approved.

    Only steps 2, 3, 5, 7, 9 and 10 are Python jobs (plus step 1, which runs inside main.py); the three *-load steps are a single CALL <schema>.sp_load_all(...) inside PostgreSQL (main.py:run_load). A failing step stops the run unless --keep-going is passed.

    Step 1 (preflight, src/utils/preflight.py) sends one cheap statement to each source - PostgreSQL, MySQL, MongoDB, Databricks - with capped exponential backoff, so an unreachable source or a rejected Databricks token stops the run before Spark starts. Airflow keeps its own banking_airflow.preflight task (Java, disk, Maven, SMTP) and runs the other nine through main.py --only <step>.

    Extracts in detail (step 2)

    The three extractors share src/utils/extract_runner.py. Each table follows the same safe, twice-runnable loop (src/utils/spark_io.py):

    sequenceDiagram
    autonumber
    participant X as extract_<source>.py
    participant A as audit
    participant S as source system
    participant P as PostgreSQL

    X->>A: fail_stale_runs(6h) · start_pipeline_run
    loop each enabled table
        X->>A: table_run(...) opens RUNNING row
        alt incremental
            X->>A: get_watermark + begin_batch (lock_version)
            X->>S: MAX(incremental_column)
            Note over X: skip when there is no new data
        end
        X->>S: Spark reads ONLY the batch window
        X->>P: write raw._stg_<table>
        X->>P: ONE transaction: promote → raw + advance_watermark
        X->>P: drop raw._stg_<table>
        X->>A: row_count_source_vs_landed
        X->>A: close table_run (SUCCESS/FAILED/SKIPPED)
    end
    X->>A: finish_pipeline_run (SUCCESS/PARTIAL/FAILED)

    Key points:

    • Snapshot, read, promote, advance. The window is [last_watermark, MAX(source col)]. Spark writes to a transient raw._stg_<table>, then one Postgres transaction promotes it to raw.<table> and advances the watermark. If anything fails before that commit, the target and watermark are untouched, so a retry simply re-extracts the same window.
    • Upper bound re-reads the boundary. MySQL/Mongo use >= on the lower bound (dedupe happens in staging); Databricks uses strict > because created_at is often shared by a whole batch (spark_io._dbx_where).
    • Schemaless sources are tamed. Mongo dates/ids arrive as strings; cast_temporal, cast_integers, and prepare_for_jdbc convert them (structs/maps → jsonb). MySQL columns get exact Postgres types from information_schema. Databricks results are streamed through Arrow to local Parquet (memory-flat, no JDBC driver).
    • Schema drift is absorbed. promote_staging creates the target on first run and adds new source columns automatically (ALTER TABLE ... ADD COLUMN).

    6. Watermarks and idempotency

    Two separate watermark stores. They must never be conflated (docs/AUDIT.md).

    flowchart LR
    subgraph EXT["extract · source → raw"]

        RAW -.->|advance in same txn| EW[("audit.extract_watermarks")]
        EW -.->|next window start| SRC
    end
    subgraph STG["staging · raw → staging"]
        RAW2[("raw.<table>")] -->|"sp_load filters > wm"| STG2[("staging.<table>")]
        STG2 -.->|advance in same block| TW[("audit.etl_watermarks")]
        TW -.->|next window start| RAW2
    end

    classDef src fill:#dbeafe,stroke:#1d4ed8,color:#1e3a8a,stroke-width:2px
    classDef raw fill:#ffedd5,stroke:#c2410c,color:#7c2d12,stroke-width:2px
    classDef staging fill:#cffafe,stroke:#0e7490,color:#164e63,stroke-width:2px

    class RAW,RAW2 raw
    class STG2 staging
    class EW,TW audit
    • audit.extract_watermarks — last source value landed into raw, advanced by advance_watermark inside the extract transaction; bootstrapped by scripts/seed_watermarks.py.
    • audit.etl_watermarks — last raw value consumed into staging, advanced by each staging.sp_load_* (defaults to _loaded_at).
    • Both use optimistic locking (lock_version): begin_batch snapshots it, advance_watermark updates WHERE lock_version = expected and raises a conflict (→ rollback) if a concurrent run won.
    • Full loads (MySQL) have no watermark and TRUNCATE + INSERT atomically, so readers never see an empty table.

    7. Audit model

    Everything is recorded in the audit schema with plain psycopg2, in its own transactions, so a FAILED record survives the data load's rollback.

    • audit.pipeline_runs — one row per execution. The three parallel per-source Airflow tasks share one row via ON CONFLICT (dag_id, dag_run_id). finish_pipeline_run rolls up using only the latest attempt per table; finalize_dag_run first reaps orphaned RUNNING rows.
    • audit.table_runs — one row per table attempt (attempt_number increments), with row counts, watermarks and execution_metadata jsonb. fail_stale_runs(6h) reaps crashed rows at job start.
    • audit.pipeline_errors — classified (CONNECTION / CONCURRENCY / SPARK / DATA / UNKNOWN), secret-redacted, linked from table_runs.error_id.
    • audit.source_registry + audit.source_tables — the config every extractor reads via get_enabled_tables (the runtime source of truth for the extract layer).
    • DQ verdicts also land in audit.dq_run / audit.dq_violation (view audit.v_dq_latest).

    8. Data-quality gates

    Each layer is gated by a SQL suite that runs against the warehouse before the next layer may load. A critical failure blocks publish. This is data testing; code testing lives in docs/TESTING.md.

    • Suites: tests/data-quality/{raw,staging,analytics,marts}/ — 10 / 10 / 13 / 11 checks (plus the DDL-only analytics/00_lp_check_upstream_freshness.sql helper function).
    • Each file defines one procedure audit.dq_<layer>_<check>() that writes audit.dq_run + audit.dq_violation, updates the verdict, COMMITs, then RAISEs on failure — the one intentional COMMIT inside SQL, so the reason survives the rollback.

    • The smoke suite (tests/smoke/test_sql_contract.py) enforces the per-file contract (master file present, unique numeric prefixes, audit.dq_* name, COMMIT-before-RAISE).

    • pyarrow writes Parquet locally (no Hadoop), files are uploaded to a UC volume, and one MERGE INTO … USING read_files(...) runs straight from the files. Missing columns are added automatically.
